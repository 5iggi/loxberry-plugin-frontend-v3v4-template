# Logging Notes

## Principle

The template log page should not scan files from `/opt/loxberry/log/plugins/<plugin>` on its own. It should use the LoxBerry log list instead:

- Perl: `loglist_html()` or `LoxBerry::Web::loglist_html()`
- PHP: `LBWeb::loglist_html()`

These functions generate the HTML code for the log list. The output is generated by LoxBerry and may contain collapsible sections, loglevel controls and links to the LoxBerry Log Viewer.

## Important: log list is not simply a file list

The visible log list is based on LoxBerry's log management. Files copied manually into the log directory are not reliably shown in this list.

If a file only exists as a normal file in `/opt/loxberry/log/plugins/<plugin>/`, it may appear in the Log Manager under "More Logfiles". This does not mean that it becomes part of the session-based `loglist_html()` output.

## Demo log in this template

The template contains a demo script:

```text
bin/create_demo_log.sh
```

This script uses the LoxBerry Bash logging library:

```bash
. "$LBHOMEDIR/libs/bashlib/loxberry_log.sh"
```

For Bash logging, the relevant variables must be set before `LOGSTART`:

```bash
PACKAGE="$PLUGIN"
NAME="demo"
LOGDIR=""
FILENAME="$LOGDIR_PLUGIN/demo.log"
APPEND=1
LOGSTART "Demo log started."
```

`PACKAGE` should match the plugin folder so LoxBerry can associate the log with the plugin.

## Why LoxBerry cleans up logs

LoxBerry actively maintains logs. The Log Manager can truncate or delete old or large logs. Cleanup can also happen when the log area or tmpfs/RAM disk is low on free space.

This means:

- Logs must not be used as persistent data storage.
- A plugin must not assume that a log file stays available forever.
- A log view must handle missing or truncated files.
- A daemon must handle the case that a log file is deleted or rotated while it is running.

## Session logs for actions

For typical web frontend actions, LoxBerry session logs are useful:

- saving configuration
- starting a service
- stopping a service
- restarting a service
- running diagnostics
- creating exports

Session logs are preferable to one large collection log because the Log Manager can display and manage them as individual sessions.

## Daemon logs

A long-running service may additionally keep its own daemon log. However, this log should be robust against external deletion or rotation.

For Python services, `WatchedFileHandler` is a suitable example because it can detect when a file has been replaced or rotated externally.

## Not recommended

- Manually copy log files into the log directory and expect `loglist_html()` to show them.
- Use logs as state storage.
- Write endlessly growing collection logs.
- Create session logs without `LOGEND` unless it is truly a long-running process.
